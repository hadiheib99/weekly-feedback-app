## Goal

An anonymous participant can submit at most one response to each weekly feedback cycle from the same browser or network. Duplicate prevention stores only salted, one-way hashes, works under concurrent requests, and gives participants a generic result that does not reveal which identifier matched.

## Acceptance criteria

- [ ] A successful public-form submission stores a 64-character lowercase SHA-256 hash in both `network_hash` and `device_hash`; neither stored value equals the raw network address or raw device identifier.
- [ ] Both hashes are derived with the server-side `FEEDBACK_HASH_SALT`, and changing that salt for the same raw identifier visibly produces a different hash.
- [ ] A participant with no `pulse_device` cookie receives a newly generated, unpredictable device identifier only after a successful submission.
- [ ] The successful-submission response sets `pulse_device` with a one-year maximum age, `HttpOnly`, `SameSite=Lax`, path `/`, and `Secure` whenever `DEBUG` is false.
- [ ] An existing `pulse_device` cookie is reused rather than replaced after a successful submission to a different cycle.
- [ ] After one response exists, a second `GET` or otherwise valid `POST` for the same cycle from the same network but a different or missing device cookie displays a generic “Unable to submit” page with HTTP status `409`, and the cycle still has exactly one response.
- [ ] After one response exists, a second `GET` or otherwise valid `POST` for the same cycle with the same device cookie but a different network displays that same generic page with HTTP status `409`, and the cycle still has exactly one response.
- [ ] The duplicate page does not state whether the network identifier, device identifier, or both matched; it does not display the feedback form or expose any stored hash or raw identifier.
- [ ] The same network and device may each submit once to a different feedback cycle; duplicate protection is scoped to a cycle rather than permanently blocking a participant.
- [ ] Two submissions to the same cycle are both accepted when both their network addresses and device identifiers differ.
- [ ] Database constraints reject a second response for the same cycle when either its `network_hash` or `device_hash` matches an existing response, even when application-level duplicate checks are bypassed.
- [ ] If two matching submissions race past the initial duplicate check, exactly one response is stored and the other request receives the same generic duplicate result instead of an unhandled database error.
- [ ] A malformed or attacker-selected `pulse_device` cookie is treated only as opaque input to the hash: its raw value is not stored, reflected in a page, or allowed to override response-owned fields.
- [ ] When no network address is available on the request, submissions use a non-empty, salted hash of a documented fallback value and fail closed: subsequent no-address submissions to that cycle receive the generic duplicate result.
- [ ] Forwarded-client headers are not trusted by default to bypass network duplicate protection; the application uses the direct request address unless a trusted-proxy policy is explicitly configured and documented.
- [ ] Invalid form submissions create no response and do not set a new device cookie; after correcting the form, the participant can submit normally.
- [ ] Automated tests visibly cover raw-value exclusion, salt use, cookie attributes and reuse, same-network/different-device duplicates, same-device/different-network duplicates, both identifiers different, identifiers reused in another cycle, malformed cookies, missing network addresses, spoofed forwarded headers, invalid forms, database constraints, and the concurrent-conflict error path.

## Constraints

- Keep implementation changes inside duplicate-protection fields and constraints in `feedback/models.py` and `feedback/migrations/`, request hashing/cookie/duplicate handling in `feedback/views.py`, the generic state template under `templates/feedback/`, `FEEDBACK_HASH_SALT` configuration in `pulse_project/settings.py`, and focused automated tests under `feedback/`.
- Preserve the `Response.network_hash` and `Response.device_hash` fields and per-cycle uniqueness contract established by [#2](https://github.com/hadiheib99/weekly-feedback-app/issues/2). Any model change must include a committed migration.
- Use Python's standard-library cryptographic hashing and secure random identifier facilities plus Django's database transaction/error handling; do not add dependencies.
- Never persist or deliberately log a raw network address or raw device identifier. Never send either raw value or either hash to templates or internal dashboards.
- Use `settings.FEEDBACK_HASH_SALT`, not a hard-coded salt. Production configuration and rotation instructions belong to [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).
- Treat a response as duplicate when either the network hash or device hash already exists for that cycle. Keep database uniqueness constraints as the final guard against concurrent requests.
- Do not trust `X-Forwarded-For` or similar client-supplied headers merely because they are present. Any proxy-aware behavior must use an explicit trusted-proxy setting and retain the same tests against spoofing.
- Preserve the availability checks from [#4](https://github.com/hadiheib99/weekly-feedback-app/issues/4) before duplicate processing and preserve the form behavior from [#3](https://github.com/hadiheib99/weekly-feedback-app/issues/3).
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
