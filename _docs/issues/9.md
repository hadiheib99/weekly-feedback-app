## Goal

Django administrators can manage projects, lead assignments, and feedback cycles through the standard Django admin, and can safely inspect—but not alter—submitted responses. Admin lists provide practical columns, search, filters, and date navigation, while ordinary project leads have no administrative access.

## Acceptance criteria

- [ ] `Project`, `FeedbackCycle`, and `Response` are visibly registered in Django admin under the feedback application.
- [ ] A superuser can open the project list, add a project with zero or multiple leads, edit its name, description, lead assignments, and active status, and delete it through Django's standard confirmation flow.
- [ ] The project list visibly shows name, active status, and creation date; it can be filtered by active status and searched by project name, description, lead username, or lead email.
- [ ] Project search results contain each matching project only once even when multiple assigned leads match the query.
- [ ] The project edit page provides a usable multi-select control for adding and removing leads, and saved assignment changes are reflected on the next dashboard request as specified in [#6](https://github.com/hadiheib99/weekly-feedback-app/issues/6).
- [ ] A superuser can open the feedback-cycle list, add a cycle for a selected project, edit its project and opening/closing timestamps, and delete it through Django's standard confirmation flow.
- [ ] The cycle list visibly shows project, opening time, closing time, and whether the cycle is currently open; it can be filtered by project, searched by project name, and navigated by opening date.
- [ ] A newly added cycle receives its unique public token automatically, and the token is visible but read-only on both add-after-save and edit pages.
- [ ] Attempting to save a cycle whose closing timestamp is equal to or earlier than its opening timestamp remains on the admin form, displays a visible validation error beside the closing time, and creates or updates no invalid cycle.
- [ ] A superuser can open the response list and response detail pages to inspect a response's cycle, score, comment, creation timestamp, network hash, and device hash.
- [ ] The response list visibly shows cycle, score, and creation timestamp; it can be filtered by score and cycle project, searched by project name, and navigated by creation date.
- [ ] Response fields are read-only in the admin, and the response admin provides no add, change, or delete action or button, preserving submitted feedback and duplicate-prevention metadata.
- [ ] Raw network addresses and raw device identifiers are absent from all admin pages because only the stored hashes from [#5](https://github.com/hadiheib99/weekly-feedback-app/issues/5) exist.
- [ ] A signed-out request to `/admin/` is redirected to the Django admin sign-in page.
- [ ] An authenticated non-staff project lead cannot open `/admin/`, any feedback model list, or any feedback model add/change/delete page; each request is denied or redirected without displaying project, cycle, response, or hash data.
- [ ] A staff user without the relevant Django model permissions cannot view or modify those models, while a staff user granted specific standard Django permissions can perform only the corresponding permitted operations.
- [ ] Deleting a project or cycle uses Django's visible protected confirmation summary before the existing cascade behavior from [#2](https://github.com/hadiheib99/weekly-feedback-app/issues/2) removes related records.
- [ ] Automated tests visibly cover all three registrations, project and cycle create/edit/delete flows, lead assignment, list columns, search, filters, date navigation, cycle validation and read-only token behavior, view-only responses, raw-value absence, signed-out access, non-staff denial, granular staff permissions, and superuser access.

## Out of scope

- Creating a custom administration interface outside Django admin is not part of the MVP and is documented as a limitation in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).
- Dashboard authentication and project-level viewing permissions are handled in [#6](https://github.com/hadiheib99/weekly-feedback-app/issues/6).
- Project overview and project result presentation are handled in [#7](https://github.com/hadiheib99/weekly-feedback-app/issues/7) and [#8](https://github.com/hadiheib99/weekly-feedback-app/issues/8).
- Generating demo administrators, leads, projects, cycles, and responses is handled in [#10](https://github.com/hadiheib99/weekly-feedback-app/issues/10).
- A full keyboard, screen-reader, color-contrast, and mobile review of Django admin itself is outside the custom application UI review in [#11](https://github.com/hadiheib99/weekly-feedback-app/issues/11) and is documented as a framework-provided limitation in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).
- Custom roles, object-level admin permissions, approval workflows, audit logs, soft deletion, bulk imports, response moderation, and hash-based search are deferred limitations documented in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).
- Automatic recurring cycle creation and notifications are deferred features documented in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).

## Constraints

- Keep implementation changes inside `feedback/admin.py` and focused admin tests under `feedback/`. Use existing project settings and root admin URL wiring; change them only if required to restore standard Django admin behavior.
- Use Django 4.2's built-in `ModelAdmin`, authentication, permissions, widgets, search, filters, date hierarchy, validation display, delete confirmation, and test client. Do not add dependencies or build custom management views.
- Use the models, validation, relationships, and cascade rules established by [#2](https://github.com/hadiheib99/weekly-feedback-app/issues/2); do not change the schema or create migrations.
- Treat Django `is_staff` as permission to enter the admin site, not automatic permission to every model. Preserve Django's standard per-model add, change, delete, and view permissions.
- Superusers have full project and cycle management access. Responses are view-only for every account, including superusers, by explicit response-admin policy.
- Keep feedback-cycle tokens read-only and automatically generated. Never allow an administrator to type or replace a public token through a form.
- Do not expose raw participant identifiers; hashes may appear only on the access-controlled, read-only response detail page and must not be editable or searchable.
- Keep participant comments safely escaped by Django admin and do not add HTML rendering for comment text.
- Do not change public feedback, duplicate detection, dashboard authorization, dashboard calculations, or demonstration-data behavior in this task.
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
