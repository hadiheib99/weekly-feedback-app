## Goal

Internal dashboard routes require Django username-and-password authentication and apply one reusable project-visibility rule. Staff administrators may access every project, while non-staff users may access only projects to which they are assigned as leads; unauthorized project existence is not disclosed.

## Acceptance criteria

- [ ] A signed-out request to `/dashboard/` redirects to the sign-in page and includes `/dashboard/` as the return destination.
- [ ] A signed-out request to `/dashboard/project/<project-id>/` redirects to the sign-in page and preserves that exact project URL as the return destination.
- [ ] The sign-in page visibly contains labelled username and password fields, a sign-in control, and no account-registration or passwordless-authentication flow.
- [ ] Submitting valid credentials signs the user in and redirects to the safe local return destination supplied by the protected route; with no return destination, it redirects to `/dashboard/`.
- [ ] Submitting an unknown username, an incorrect password, or blank credentials leaves the user signed out and redisplays the sign-in page with a visible generic “username or password is incorrect” message that does not identify which value failed.
- [ ] An authenticated user can sign out through the visible “Sign out” control; afterward, requesting an internal dashboard route redirects to sign-in again.
- [ ] An external or protocol-relative return destination supplied to sign-in is ignored, and successful authentication redirects to `/dashboard/` rather than leaving the application.
- [ ] A reusable project-visibility rule returns every project, including inactive projects, for a staff user and returns only explicitly assigned projects for a non-staff user.
- [ ] A non-staff project lead can open the detail route for each project assigned to that user, including an assigned inactive project.
- [ ] A staff administrator can open the detail route for any existing project, whether active or inactive and whether or not the administrator is assigned as a lead.
- [ ] An authenticated non-staff user receives the standard not-found page with HTTP status `404` when requesting an unassigned project; the page does not reveal the project's name, description, status, cycle dates, response totals, scores, comments, or lead assignments.
- [ ] An authenticated request for a project ID that does not exist receives the same HTTP status and visible not-found result as an unauthorized-project request.
- [ ] A non-staff user with no project assignments may open `/dashboard/` but cannot open any project detail route.
- [ ] Assigning a lead to or removing a lead from a project changes that user's access on the next request without requiring a new login.
- [ ] Public home, feedback-form, unavailable-state, and confirmation routes remain accessible without authentication as specified in [#3](https://github.com/hadiheib99/weekly-feedback-app/issues/3) and [#4](https://github.com/hadiheib99/weekly-feedback-app/issues/4).
- [ ] Automated tests visibly cover anonymous redirects for every internal route, valid and invalid sign-in, safe and unsafe return destinations, sign-out, assigned and unassigned lead access, assignment removal, users with no assignments, staff access without assignment, inactive-project access, indistinguishable missing/unauthorized projects, and unchanged public access.

## Constraints

- Keep implementation changes inside authentication settings and URL wiring in `pulse_project/settings.py` and `pulse_project/urls.py`, reusable authorization code and internal-route decorators in `feedback/views.py`, authentication/navigation templates under `templates/`, and focused automated tests under `feedback/`.
- Use Django 4.2's built-in authentication, session, password-hashing, login-required, and safe-redirect facilities. Do not add dependencies or create a custom user model.
- Use `settings.AUTH_USER_MODEL` and the `Project.leads` relationship established by [#2](https://github.com/hadiheib99/weekly-feedback-app/issues/2); this task must not alter the data schema or create migrations.
- Define administrators for internal project visibility as authenticated users with `is_staff=True`. Superusers receive the same visibility through their staff status.
- Keep authorization in one reusable queryset or equivalent policy used by every internal project lookup. Do not rely only on hiding links in templates.
- Return `404`, not `403`, for both nonexistent and existing-but-unauthorized project IDs so the response does not confirm project existence.
- Project `is_active` controls public collection, not retention of authorized historical results. Authorization therefore includes assigned inactive projects; issue [#7](https://github.com/hadiheib99/weekly-feedback-app/issues/7) may independently limit its overview to active projects.
- Preserve CSRF protection and reject unsafe external return URLs. Do not log credentials or include passwords in URLs, templates, or test output.
- Do not change public feedback behavior, result calculations, dashboard presentation, model fields, admin configuration, or demonstration data in this task.
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
