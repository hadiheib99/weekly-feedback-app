## Goal

Participants can view and submit a cycle-specific feedback form only when its project is active and the current time is within the cycle's opening and closing timestamps. Every unavailable public-link and home-page case has a clear, non-leaking result and creates no response.

## Acceptance criteria

- [ ] A `GET` request to `/feedback/<cycle-token>/` displays the feedback form when the cycle's project is active and the current time is between `opens_at` and `closes_at`, inclusive.
- [ ] A `POST` request containing otherwise valid feedback during that same availability window creates exactly one response and follows the successful-submission behavior specified in [#3](https://github.com/hadiheib99/weekly-feedback-app/issues/3).
- [ ] At the exact `opens_at` timestamp, both `GET` and an otherwise valid `POST` are accepted as open-cycle requests.
- [ ] At the exact `closes_at` timestamp, both `GET` and an otherwise valid `POST` are accepted as open-cycle requests.
- [ ] Before `opens_at`, a direct `GET` or `POST` to the cycle link displays an unavailable page that visibly says the check-in is not currently open; it does not display the feedback fields and a `POST` creates no response.
- [ ] After `closes_at`, a direct `GET` or `POST` to the cycle link displays a closed page that visibly says the check-in is closed; it does not display the feedback fields and a `POST` creates no response.
- [ ] When the linked cycle belongs to an inactive project, a direct `GET` or `POST` displays a generic unavailable page that does not reveal the project name, description, cycle dates, or whether the token belongs to a real cycle; a `POST` creates no response.
- [ ] A request using an unknown or malformed cycle token receives the standard not-found page with HTTP status `404` and creates no response.
- [ ] Availability is checked again for every `POST`: if a participant loaded an open form but submits after the cycle closes or after its project becomes inactive, the response is rejected and nothing is saved.
- [ ] A request to `/` redirects to the public form for an available cycle when at least one active project has an open cycle.
- [ ] If more than one cycle is available, `/` consistently redirects to the available cycle with the latest `opens_at`; if those timestamps are equal, the cycle with the lowest database ID is selected.
- [ ] If no active project has an open cycle—including when the database is empty or contains only future, expired, or inactive-project cycles—`/` displays an empty state saying that no active feedback cycle is available and does not expose a form.
- [ ] Automated tests visibly cover active, exact-boundary, future, expired, missing-token, inactive-project, changed-between-GET-and-POST, multiple-open-cycle, and no-open-cycle cases for both display and submission behavior where applicable.

- Device and network hashing, cookie behavior, database uniqueness enforcement, and duplicate-submission screens are handled in [#5](https://github.com/hadiheib99/weekly-feedback-app/issues/5).
- Sign-in and authorization for internal dashboards are handled in [#6](https://github.com/hadiheib99/weekly-feedback-app/issues/6).
- Project-list and project-results display behavior is handled in [#7](https://github.com/hadiheib99/weekly-feedback-app/issues/7) and [#8](https://github.com/hadiheib99/weekly-feedback-app/issues/8).
- Creating, editing, activating, deactivating, or automatically scheduling projects and cycles is handled through the administration work in [#9](https://github.com/hadiheib99/weekly-feedback-app/issues/9); automatic recurring cycle creation remains a deferred feature documented in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).
- A complete accessibility, responsive-layout, and visual-design review of the unavailable states is handled in [#11](https://github.com/hadiheib99/weekly-feedback-app/issues/11).
- Detailed operational and privacy documentation for public-link availability is handled in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).

## Constraints

- Keep implementation changes inside the public availability and home-page code in `feedback/views.py`, their routes in `feedback/urls.py`, state templates under `templates/feedback/`, existing feedback styles only where needed, and focused automated tests under `feedback/`.
- Use the `Project.is_active`, `FeedbackCycle.opens_at`, `FeedbackCycle.closes_at`, and `FeedbackCycle.is_open` behavior established by [#2](https://github.com/hadiheib99/weekly-feedback-app/issues/2); this task must not change the data schema or create migrations.
- Use Django's timezone-aware `django.utils.timezone.now()` for availability comparisons. An open interval is inclusive: `opens_at <= now <= closes_at`.
- Apply the same availability rule before rendering a form and before processing a submission. An unavailable request must never create a `Response`.
- Future and expired pages may explain timing status, but inactive-project and unknown-token responses must not disclose whether a project or cycle exists.
- Do not add dependencies. Use Django 4.2 and the project's existing templates, URL conventions, and test framework.
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
