## Goal

A developer can run one documented management command against a migrated local database and receive a complete, immediately usable demonstration environment. Re-running the command reconciles the same named demo records without duplicating them or changing unrelated data.

## Acceptance criteria

- [ ] Running `python manage.py seed_demo` with `DEBUG=True` exits successfully and visibly prints “Demo data is ready”.
- [ ] On an empty migrated database, the command creates exactly two demo users: a staff/superuser administrator named `demo-admin` and a non-staff project lead named `demo-lead`.
- [ ] The documented demo passwords successfully authenticate both users through the application sign-in page; `demo-admin` can enter Django admin and `demo-lead` cannot.
- [ ] The command creates at least two clearly named active demo projects; `demo-lead` is assigned to exactly one of them so the lead and administrator dashboards visibly demonstrate different project visibility.
- [ ] The command creates at least one currently open cycle and one closed cycle, with valid timezone-aware timestamps and closing times later than opening times.
- [ ] At least one demo project has both an open and a closed cycle so the results page visibly demonstrates deterministic latest-cycle selection.
- [ ] The command creates representative responses whose scores include `1` and `5`, at least one intermediate score, at least one non-empty comment, and at least one blank comment.
- [ ] Every seeded response has a valid score and distinct 64-character lowercase hexadecimal network and device hashes within its cycle; no raw network address or device identifier is stored.
- [ ] The printed output visibly includes the administrator username/password, lead username/password, dashboard URL, Django admin URL, and a cycle-specific public feedback URL for a cycle that is open when the command finishes.
- [ ] Following the printed public URL displays an available feedback form, and both demo credentials open the signed-in dashboard without requiring manual database edits.
- [ ] Running the command a second time leaves the number of command-owned users, projects, cycles, and responses unchanged and prints the same command-owned record identities rather than creating suffixed or replacement records.
- [ ] If a command-owned demo record already exists but has drifted—for example a demo project is inactive, the lead assignment is missing, or a demo user's role/password changed—the next run restores the documented demo state without duplicating the record.
- [ ] Records whose usernames and project identities are not owned by the demo command remain unchanged after the command runs.
- [ ] A failure partway through seeding leaves none of that run's partial demo changes committed.
- [ ] Running the command with `DEBUG=False` refuses to create or reset demo users or data, exits with a visible safety message, and leaves the database unchanged.
- [ ] `README.md` visibly documents the exact seed command, states that it is for local demonstration only, lists both demo credentials, and explains that the command output contains the current public link.
- [ ] Automated tests visibly cover the clean-database result, user roles and authentication, project visibility, open/closed timestamps, representative and anonymous response data, required output, second-run idempotence, drift reconciliation, unrelated-record preservation, transactional rollback, and the `DEBUG=False` safety refusal.

## Constraints

- Keep implementation changes inside `feedback/management/commands/seed_demo.py`, any command support modules under `feedback/management/`, focused command tests under `feedback/`, and the demo-specific section of `README.md`.
- Use Django's management-command, ORM, password-hashing, timezone, settings-override, and transaction facilities. Do not add dependencies, use fixtures, or write directly to the database outside the ORM.
- The command must be non-interactive and deterministic in record identity while using timestamps relative to the run time so its designated open cycle is open and its designated closed cycle is closed when the command completes.
- Define stable command-owned usernames and project identities in the implementation. Reconcile those records on repeat runs, but never delete or mutate unrelated users, projects, cycles, or responses.
- Set demo passwords through Django's password API; never store plaintext passwords in database fields. Plaintext credentials may appear only in local-demo documentation and command output and must be explicitly labelled unsafe for production.
- Derive seeded response hashes with the same salted hashing contract as [#5](https://github.com/hadiheib99/weekly-feedback-app/issues/5). Use deterministic, synthetic identifiers so repeat runs locate the same responses without storing raw values.
- Wrap all database mutations from one command invocation in a single atomic transaction.
- Refuse to run when `settings.DEBUG` is false. Do not add a force flag that can seed production accidentally.
- Do not change model fields, create migrations, alter application authorization, or make network requests.
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
