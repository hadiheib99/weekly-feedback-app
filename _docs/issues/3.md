## Goal

Anyone with a feedback cycle's public link can submit one anonymous weekly project-health response without signing in. The page clearly identifies the project, collects a required 1–5 score and an optional comment, explains the relevant anonymity boundary, and confirms a successful submission.

## Acceptance criteria

- [ ] Opening `/feedback/<cycle-token>/` for an eligible cycle while signed out displays a public feedback form without redirecting to sign-in.
- [ ] The form visibly shows the project's name, a weekly check-in prompt, five score choices labelled `1` through `5`, an optional comment field, and a submit button.
- [ ] The score scale visibly identifies `1` as the critical end and `5` as the excellent end.
- [ ] The page visibly states that the response is anonymous and that project leads cannot see the protected device and network identifiers used for duplicate prevention.
- [ ] Submitting any one of the integer scores `1`, `2`, `3`, `4`, or `5` with an empty comment creates exactly one response for the cycle with that score and a blank comment.
- [ ] Submitting a valid score with a comment creates exactly one response for the cycle and preserves the submitted comment.
- [ ] A successful submission redirects to a confirmation page that visibly names the project and states that the anonymous feedback was submitted.
- [ ] Submitting the form without a score does not create a response and redisplays the form with a visible instruction to choose a score from 1 to 5.
- [ ] Submitting a score outside `1` through `5`, a decimal, or non-numeric text does not create a response and redisplays the same visible score-validation instruction.
- [ ] When validation fails, the participant's submitted comment remains visible in the form so it can be corrected without retyping.
- [ ] Values for the cycle, project, network hash, device hash, or creation timestamp supplied as extra form fields are ignored and cannot override server-selected response data.
- [ ] Automated tests visibly cover signed-out access, every valid boundary and intermediate score, a blank comment, a non-empty comment, successful confirmation, missing and malformed scores, preservation after validation failure, and ignored extra fields.

## Out of scope

- Generating or hashing device/network identifiers, setting cookies, enforcing one response per cycle, and showing duplicate-submission states are handled in [#5](https://github.com/hadiheib99/weekly-feedback-app/issues/5).
- Sign-in and authorization for internal project results are handled in [#6](https://github.com/hadiheib99/weekly-feedback-app/issues/6).
- Displaying submitted responses, aggregates, and comments to authorized users is handled in [#7](https://github.com/hadiheib99/weekly-feedback-app/issues/7) and [#8](https://github.com/hadiheib99/weekly-feedback-app/issues/8).
- A full keyboard, screen-reader, color-contrast, and responsive-layout review is handled in [#11](https://github.com/hadiheib99/weekly-feedback-app/issues/11).
- Detailed privacy, security-assumption, setup, and operational documentation is handled in [#12](https://github.com/hadiheib99/weekly-feedback-app/issues/12).

## Constraints

- Keep implementation changes inside `feedback/forms.py`, the public feedback and confirmation views/routes in `feedback/views.py` and `feedback/urls.py`, their templates under `templates/feedback/`, existing feedback styles where necessary, and focused automated tests under `feedback/`.
- Use Django's existing forms, validation, CSRF protection, URL routing, templates, and test framework; do not add dependencies.
- Use the `Project`, `FeedbackCycle`, and `Response` model fields established by [#2](https://github.com/hadiheib99/weekly-feedback-app/issues/2); this task must not change the data schema or create migrations.
- Associate the response with the cycle resolved from the URL on the server. Do not expose identity fields or accept model-owned metadata from participant input.
- Keep the public form accessible without authentication and do not expose prior responses, response totals, comments from others, lead names, or internal dashboard links as part of the form flow.
- Preserve the existing product wording unless changing it is necessary to satisfy an acceptance criterion.
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
