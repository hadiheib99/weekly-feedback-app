## Goal

The database can persist projects, their assigned leads, weekly feedback cycles, and anonymous 1–5 responses with optional comments. The schema enforces the essential validity rules and has automated model tests that document its behavior.

## Acceptance criteria

- [ ] `feedback/models.py` visibly defines `Project`, `FeedbackCycle`, and `Response` models, and a committed migration creates all three tables without prompting for input.
- [ ] A `Project` visibly stores a required name of at most 160 characters, an optional description, an active/inactive flag defaulting to active, and its creation timestamp.
- [ ] A project can visibly have zero, one, or multiple lead users, and one user can be assigned as lead to multiple projects.
- [ ] A `FeedbackCycle` visibly belongs to exactly one project and stores opening and closing timestamps plus an automatically generated, non-editable public token that is unique across cycles.
- [ ] Creating or validating a cycle whose closing timestamp is equal to or earlier than its opening timestamp visibly produces a validation error and does not save an invalid cycle through normal model validation.
- [ ] A cycle reports itself open at its exact opening and closing timestamps, closed before opening, and closed after closing; automated tests visibly cover all four boundary cases using timezone-aware timestamps.
- [ ] A `Response` visibly belongs to exactly one cycle, stores an integer score from 1 through 5, permits a blank comment, and records its creation timestamp.
- [ ] Model validation visibly accepts scores `1` and `5` and rejects scores `0`, `6`, negative values, non-integer values, and a missing score.
- [ ] The response schema contains no user, email, name, or other direct participant-identity field.
- [ ] Deleting a project visibly deletes its cycles and their responses, while deleting a lead user leaves the project and its feedback data intact.
- [ ] Default query ordering visibly returns feedback cycles newest-opening-first and responses newest-created-first.
- [ ] Human-readable model labels visibly show the project name for a project and include both the project name and cycle date for a feedback cycle.
- [ ] Running `python manage.py makemigrations --check --dry-run` visibly reports that no model changes are missing from migrations.
- [ ] Running `python manage.py test` visibly completes with `OK`, including focused tests for field rules, relationships, deletion behavior, ordering, cycle validity, and open/closed boundaries.

## Constraints

- Keep implementation changes inside `feedback/models.py`, `feedback/migrations/`, and model-focused tests in `feedback/tests.py` or a dedicated test module under `feedback/`.
- Use Django's configured user model through `settings.AUTH_USER_MODEL`; do not hard-code Django's default `User` class.
- Use Django model fields, validators, constraints, and migrations; do not add a new dependency.
- Use timezone-aware values through Django's timezone utilities.
- Preserve anonymity by keeping direct participant identity out of `Response`; duplicate-protection metadata belongs to #5.
- Do not modify routes, views, forms, templates, dashboards, authentication configuration, or admin presentation in this task.
- Follow [`AGENTS.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/AGENTS.md), [`_docs/process.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/process.md), and [`_docs/task-template.md`](https://github.com/hadiheib99/weekly-feedback-app/blob/master/_docs/task-template.md).
